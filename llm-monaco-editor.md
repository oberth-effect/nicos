# The Monaco script editor

A variant of the NICOS GUI editor panel with the
[Monaco editor](https://microsoft.github.io/monaco-editor/) (the editor of
VS Code), embedded through the `qtmonaco` package, instead of QScintilla.  It
adds code assist for the commands and devices of the connected daemon:
completion, hover help and signature help, including the results of
type-annotated user methods.

`MonacoEditorPanel` is a subclass of `EditorPanel`, which itself is
unchanged.  Everything else of the editor panel works as before: file
handling, the script browser, Run, Dry run, Update and Get, the dry-run
result pane, recent files and the reopening of files at startup.

This document describes the features and, in detail, which requests the
code assist sends to the daemon and when.

## Enabling it

In a guiconfig, use the panel class instead of `EditorPanel`; it takes the
same options:

```python
panel('nicos.clients.gui.panels.monacoeditor.MonacoEditorPanel')
```

Requirements:

* `qtmonaco>=0.11,<0.12` (listed in `requirements-opt.txt`), which needs
  Python 3.10 or newer; the rest of NICOS keeps working on 3.9.  It depends on
  `qtpy` and `python-lsp-server`, which it starts as a subprocess of the GUI.
* PyQt6 with `PyQt6-WebEngine`, and `NICOS_QT=6`.  The Qt 5 bindings are not
  supported by `qtmonaco`.

If `qtmonaco` cannot be imported, the panel module raises ImportError, and
the GUI logs "Could not import class" and leaves the panel out, as for other
panels with a missing optional dependency.

The daemon side needs `Session.getNamespaceInfo()`, i.e. a NICOS of the same
version.  Against an older daemon the editor works, but without code assist
for NICOS names; one warning is logged per connection.

## Editing features

* **One editor view per panel.**  All open scripts are models in a single
  Monaco view; the tab bar above it switches between them.  Each extra tab
  therefore costs only a text model, not another browser view (a view costs
  about 110 MB and a renderer process; the first one, including the browser
  and the language server processes, about 600 MB).
* **Monaco editing.**  Multi-cursor editing, bracket matching and
  auto-closing, folding, indentation guides, word wrap, 4 spaces per
  indentation level, Python syntax highlighting.
* **Find and replace** (Ctrl+F, Edit menu) opens Monaco's own find widget,
  with regular expressions, case and whole word options.  It replaces the
  separate search dialog of the QScintilla editor.
* **Comment toggling** (Edit menu, Ctrl+#) uses Monaco's line comment action,
  configured with the NICOS comment prefix `##`, so the result is the same as
  with QScintilla.  It works on the selection or the current line and
  supports multiple cursors.
* **Syntax check.**  400 ms after the last change the text is compiled with
  Python's `compile()` in the GUI process, and a syntax error is shown as an
  error marker (red squiggle, hover shows the message).  Nothing is sent to
  the daemon for this.  The check uses the Python version of the GUI.
* **Text files.**  Files with the extension `.txt` (simple parameter mode
  scripts) are shown as plain text: no Python highlighting, no syntax check,
  no code assist.  The language is switched when a file is opened or saved
  under a new name.
* **Style.**  The user font and background color of the GUI (Options menu)
  are applied to the editor; the theme (light or dark) follows the lightness
  of the background color.
* **Printing** prints the text with the editor font through a
  `QTextDocument`.  Unlike the QScintilla printer it has no page header.
* **Clipboard, undo, redo** from the Edit menu use the web page's clipboard
  actions and Monaco's undo stack; the keyboard shortcuts work as in VS
  Code.  Code generated by the command builder is inserted as one undo
  step.
* **Saving and running.**  The text lives in the page.  Whenever the panel
  needs the text or the modified state (save, run, dry run, update, closing
  a tab or the GUI, a file changed on disk), it asks the page and waits for
  the answer, a few milliseconds, in a local event loop that excludes user
  input; so it never misses an edit made just before.  The page reports the
  modified state as it changes, for the `*` in the tab, and is unmodified
  again when undo returns to the saved text.  A byte order mark at the start
  of a file is kept.

## Code assist

### How it works

Completion, hover and signature help come from jedi, in the language server
(`pylsp`) that `qtmonaco` runs as a subprocess of the GUI.  jedi knows Python,
the packages of the GUI's environment and the script itself: assignments,
loops, imports, functions.  It learns the NICOS names from two stub modules
that the daemon writes, as part of its catalog, and the GUI puts into a
temporary directory:

* `_nicos_types` has one class per device class and per class reached
  through type annotations: the user parameters of devices as properties,
  all their public methods, and the attributes and methods of other
  classes, annotated with the names of the stubs.  It also has the user
  commands as functions.
* `nicos_session` imports the commands from `_nicos_types` and declares each
  device with its class.

For example (shortened):

```python
# _nicos_types.py
class Foo:
    'Demonstration device ...\n\nNICOS readable nicos_demo....Foo'
    def history(self, count: int = 5) -> List[Bar]:
        'Return the last *count* readings, oldest first.'

class Bar:
    @property
    def label(self) -> str:
        'A short label of the reading.'

def maw(dev, pos, *args):
    'maw(dev, pos, ...)\n\nMove one or more devices to a new position ...'

# nicos_session.py
from _nicos_types import maw
Foo: _nicos_types.Foo
'device with annotated user methods, see the help of the editor panel'
```

The stub directory is on jedi's path, and the editor prepends
`from nicos_session import *` to every document it sends to the language
server (`qtmonaco` shifts the positions back).  To jedi a NICOS script is
then plain Python, so `Foo.history()[0].`, `for r in Foo.history(): r.`,
`x = Foo.latest()` followed by `x.`, tuple unpacking and the like all
resolve.  The class names in the stubs cannot shadow devices, since
`_nicos_types` itself is not star-imported; a device and its class may
have the same name.

Signatures: a NICOS `help_arglist` is used as the signature if it is valid
Python, after a trailing `...` becomes `*args` (`maw(dev, pos, *args)`);
otherwise the real signature of the function is used, and the
`help_arglist` text is the first line of the docstring.  Docstrings are
converted to Markdown by the language server (`docstring_to_markdown`).

The stubs are rewritten whenever the catalog changes; jedi reads them anew
for the next request.

### Sources and daemon requests

| Source | Knows | Daemon request |
|---|---|---|
| **jedi with the stubs** | NICOS commands, devices, their parameters and user methods, the classes reached through annotations; Python itself, installed packages, names defined in the script | the catalog: one `eval` of `session.getNamespaceInfo()` |
| **Daemon completer** | attributes of objects that only the daemon knows, e.g. variables of a script that has run | `complete` |
| **Live device values** | current value, target, status and limits of a device; current value of a parameter | `getcachekeys` (through `client.getDeviceParams` and `client.getDeviceParam`) |

The two daemon requests besides the catalog are answered in a thread of the
GUI, so that they never block typing; the page waits at most 4 s for them.

**Catalog fetch**

* **When:** 500 ms after the last of the client events `connected`, `setup`
  or `device` (the delay collects the bursts of events of a setup change).
  Cleared when the client disconnects.
* **What:** one `eval` of `session.getNamespaceInfo()`
  (`nicos.core.sessions.introspect`).  The daemon reads the exported names
  of the script namespace, the class dictionaries (parameters, methods,
  annotations, docstrings) and the cached description and unit of each
  device, and returns the sources of the two stub modules, the user API of
  each device class (its user methods and parameters, which the suggestion
  list marks), and the name, class, description and unit of each device and
  the summary of each command for the hovers and suggestions.  It executes
  no device or user code: attributes are read with `inspect.getattr_static`
  and signatures with `inspect.signature`.  String annotations (and all
  annotations under `from __future__ import annotations`) are evaluated one
  by one with `typing.get_type_hints()`, in the namespace of the module that
  defines them, on copies of the namespaces; type expressions have no side
  effects.  One that cannot be evaluated, e.g. for an unknown name, or
  `X | Y` on a Python 3.9 daemon, is written as a string, which jedi may
  still resolve.  Classes reached through annotations are written up to a
  distance of 3 from the devices and at most 400 classes.  The GUI needs no
  NICOS classes for this, and writes the stubs as they come.
* **Size:** about 100 kB for the demo setup, mostly the docstrings of the
  commands; each device class is written once.
* **Failure:** an older daemon returns an exception object for the
  expression; the editor then knows no NICOS names and logs one warning.

**Completion** comes from jedi.  In addition, for the members of a dotted
name, e.g. `s.` or `s.cfg.`, the daemon's completer is asked if the first
name is neither a command nor a device and jedi cannot complete the
expression either (checked with jedi in the GUI process, on the same
stubs).  This is the daemon's existing completer, also used by the console
on Tab: it evaluates the dotted name in the script namespace and reads every
attribute of the object that matches the typed prefix.  Reading an
attribute executes parameter getters and properties; a volatile parameter
is read from hardware.  Methods are only looked up, never called.  The
results are shown with the detail "from the NICOS session".  The setting
"Ask the daemon about members of unknown names" switches this request off.

In the list, the commands are marked "NICOS command" and the devices with
their class, with the first line of the docstring or the description of the
device as the detail.  After a dot, the user API of a device, its user
methods and parameters, is marked "user method" and "parameter"; its other
public methods, the internal ones and those for drivers (`doRead()` etc.),
are offered once a name is typed, and private members of any value once the
name begins with `_`, much as in the console.  Python tells which members
belong to the user API, from the stub class jedi takes them from.  The
editor adds this to the items of the language
server, by wrapping the completion provider of `qtmonaco`; the wrapper also
gives the items the kinds of Monaco, since `qtmonaco` passes on those of
the language server, which are numbered differently, so that the icons would
be wrong.  The items have no documentation in the list: `qtmonaco` does not
ask the server to resolve them, and resolving all of them at once (the
`eager` option of the server) makes a completion take seconds.  Commands,
functions and methods are inserted as a call, `name()` with the cursor
between the brackets and the parameter hints open; the language server
alone would insert the bare name, since the client of `qtmonaco` declares no
snippet support.

**Hover** comes from jedi: signatures and docstrings of commands, methods
and classes.  For other values the language server shows only the docstring
of their type, so the editor adds the type itself, as jedi in the GUI
process infers it: `lst: list[Bar]` after `lst = Foo.history()`, `x: Bar`
after `x = Foo.latest()`, `y: int | str` for alternatives.  When the
language server cannot document a name, because jedi infers no value or
several for it (e.g. a parameter of a union type such as `none_or(...)`, or
one whose type has no Python equivalent), the hover shows its type, if any,
and its description from the stub; a parameter of a single type is
documented by the language server itself, with its type and description.
For a device name it adds its class, description, whether it is an alias,
and its current value, target, status and user limits
(`getcachekeys <device>/`, served from
the daemon's cache copy, no device code).  The status is colored like in the
device panel.  For a parameter after a device name, e.g. `motor.speed` or
`mot.speed` for an alias, it adds the current value of the parameter
(`getcachekeys <device>/<parameter>`, of the aliased device for an alias),
long values shortened; members that jedi resolves to methods get no value,
even if the cache has a key of that name, such as `status`.  The setting
"Show current device values in tooltips" switches both requests off; the
descriptions are shown anyway.

**Signature help** comes from jedi, with the active parameter highlighted.

**Never**

The editor never evaluates expressions typed into it in the daemon, never
calls methods, never constructs objects and never writes anything.  The
daemon's state is only read through the catalog (class metadata), the cache
(hover values) and, in the one case described above, the daemon's
completer.

### Making a device "typed"

Annotate the user methods with their return types; string annotations and
`from __future__ import annotations` work.  Properties contribute the return
annotation of their getter, dataclass fields and other annotated class
attributes contribute their annotation.  Lists, sets, dicts, tuples and
unions (`Bar | None`, `Optional[Bar]`) are followed.  NICOS parameters get
the type of their values: a plain Python type (`float`, `int`, ...) as it
is, and the converters of `nicos.core.params` mapped to the type of the
values they give, e.g. `floatrange` to `float`, `listof(str)` to
`List[str]`, `none_or(...)` to `Optional[...]`, `oneof` to the types of its
values, `setof` to a list of them (the stubs write sets as lists) and
`limits` to a tuple of two floats.  Converters not listed in the mapping,
such as `anytype`, those of facility modules and subclasses of the mapped
ones, give no type.

The demo instrument contains a worked example: setup `editordemo` with the
device `Foo` (`nicos_demo/demo/devices/editordemo.py`), whose methods return
a `Bar`, a `list[Bar]`, a `dict[str, Bar]` and an
`Optional[tuple[Bar, Bar]]`.
Try `Foo.history()[0].`, `Foo.byLabel()['reading 3'].` or `for r in
Foo.history():` followed by `r.` on the next line.

### Settings

The toolbar button "Editor settings" (also in the View menu of the panel)
opens a dialog with the settings of the editor.  They are stored with the
other settings of the panel, in the `monaco` subgroup of the `User editor`
group of the GUI's `QSettings`, so a GUI without the Monaco editor keeps
them and ignores them.  Changes apply immediately to the open documents.

| Setting | Default | Effect |
|---|---|---|
| Comment prefix | `##` | inserted and removed by the Comment action; a space is added after it |
| Indentation width | 4 | spaces per indentation level |
| Wrap long lines | on | |
| Show the minimap | off | |
| Mark syntax errors | on | the local `compile()` check |
| Show suggestions while typing | on | otherwise suggestions appear only after a dot or with Ctrl+Space |
| Ask the daemon about members of unknown names | on | the `complete` request described above; off means completion never contacts the daemon |
| Show current device values in tooltips | on | the `getcachekeys` requests on hover, for devices and their parameters |
| Suggest words of the document | off | Monaco's word based suggestions |
| Suggest code snippets | off | the snippets shipped by `qtmonaco`, offered regardless of context |
| Match suggestions despite small typos | off | Monaco's typo tolerant filter, which also matches with two adjacent typed characters swapped; with it, typing `Foo(` leaves `format(value, format_spec)` as the only suggestion |

Not configurable: suggestions are never shown inside comments and strings,
and the linters, style checkers and auto-import of the language server stay
disabled, since the editor's own syntax check covers that.

## Console completion

The console panel, the command line panel and the command builder panel
(`nicos.clients.gui.panels.cmdbuilder.CommandPanel`) can use the same stubs
for their input line, with the guiconfig option `completion='jedi'`:

```python
panel('nicos.clients.gui.panels.console.ConsolePanel', completion='jedi')
```

Tab completion of members, after a dot, then uses jedi in the GUI process,
so that e.g. `Foo.latest().` or `motor.getBars()[0].` are completed, in the
format of the daemon's completer: callables end in `(`.  Everything else,
and members that jedi does not know, are completed by the daemon's
completer as without the option, so setup names, modes and the variables of
the script namespace are completed as before.  This needs the `jedi`
package, which `qtmonaco` installs with the language server.

## Architecture in brief

* `nicos/core/sessions/introspect.py` writes the stub modules and the rest
  of the catalog in the daemon (`Stubs`); `Session.getNamespaceInfo()`
  exposes it.  The module docstring documents the stubs.
* `nicos/clients/gui/completion.py`: `Catalog` fetches the catalog, one per
  client, shared by all front ends, and writes the stub modules into its
  directory (`writeStubs`); `CodeAssist` adds the device hover, the
  members from the daemon's completer and the console completion.
* `nicos/clients/gui/widgets/monacoeditor.py` holds the host view
  (`MonacoHost`, a `qtmonaco.Monaco` web view), the document handles
  (`MonacoDocument`, the tab pages with the QScintilla-shaped API the panel
  uses) and the settings dialog.  The host gives the language server the
  stub directory and the header before the page connects to it (`qtmonaco`
  sends both only when it connects), and answers the requests of the page in
  threads.
* `nicos/clients/gui/widgets/monacoeditor.js` is injected into the page: it
  manages the models, tracks their modified state and registers the two
  providers for the device hover and the members from the daemon.
* `nicos/clients/gui/panels/monacoeditor.py`: `MonacoEditorPanel`, the
  subclass of `EditorPanel` that creates the documents in the host and
  overrides the few actions that differ (find, comment, print, the file
  type, closing a tab); `console.py`, `commandline.py` and `cmdbuilder.py`
  hook the console completion into their input line, the callback that
  `lineCompleter` in `assist.py` returns.

Communication inside the GUI: Python sends commands to the page with
`runJavaScript` (`window.nicosEditor.handle({...})`) and queries the text and
the modified state the same way, waiting for the answer.  The page sends its
events and requests to the `nicos` object (`MonacoBridge`) that the host
registers on the web channel of the view; the answers to requests come back
through its `answered` signal.  The language server is reached by
`qtmonaco`'s client in the page, over a WebSocket on localhost.

The editor relies on four details of `qtmonaco`, the reason for the version
pin: its `_load_editor()` method, overridden to inject the script before
the page loads; its `_set_host()` method, called to connect the page to a
language server started again (see below); the `QWebChannel` constructor
of the page, wrapped to get the channel, which `qtmonaco` keeps to itself;
and the registration of its completion provider through
`monaco.languages`, wrapped to adapt the items.

## Known limitations

* Screen blink when opening a window with a web view (Windows).  Qt
  composites web views, the Monaco editor as well as the logbook and help
  pages, through its Qt Quick scene graph, by default with Direct3D;
  creating the Direct3D swap chain of a new window with a web view makes
  the screen blink on some machines, notably laptops with hybrid graphics,
  every time such a window is opened.  Starting the GUI with the
  environment variable `QT_QUICK_BACKEND=software` avoids this.  Qt
  WebEngine supports that backend; it costs GPU acceleration of web
  content, which these pages do not need.  NICOS does not set it by
  default.
* `qtmonaco` is an alpha-quality package; the version is pinned below 0.12.
* `qtmonaco` starts the language server unconditionally and installs its own
  SIGINT/SIGTERM handlers, which only stop the server.  The editor chains
  them to the previous handlers, so these signals still act on the GUI as
  without the Monaco editor, after the server is stopped.
* pylsp ends its WebSocket server when a client disconnects while an answer
  is sent to it (`ConnectionClosedOK` in `pylsp/python_lsp.py`), e.g. when a
  window with an editor is closed during a request, and with it the
  completion of all editors.  A watchdog (`ServerWatchdog`) checks the
  server every 2 s, starts it again on the same port and connects the pages
  anew, since `qtmonaco`'s client reconnects by itself only to a server
  that ended after the connection was initialized.  A server that ends
  again within a minute of each of 3 restarts is given up, with a warning.
* `qtmonaco` sends the text of the shown document to Python on every
  keystroke, for its own `text_changed` signal; the editor sends it only
  after a pause in typing, for the syntax check.
* The daemon completer, used for members of unknown names, executes
  parameter getters and properties in the daemon, as the console always has.
  Member completion of names bound to devices by running a script therefore
  reads volatile parameters from hardware.
* The first answer of jedi after the start of the GUI takes about half a
  second, a large package such as numpy a few seconds on first use.
* The private stub module `_nicos_types` is offered as a completion when
  typing a name starting with `_`: jedi does not hide such names of star
  imports.
* Printing has no page header; the separate search dialog is replaced by
  Monaco's find widget.
